# Smart-ProfiHub — MVP

Внутрішня корпоративна AI-платформа: централізований доступ до моделей ШІ
(LLM/CV) у контурі Azure AI Foundry, рольова модель (RBAC), групи, каталог
скілів та базовий облік токенів.

Цей репозиторій містить **MVP веб-додатка**: REST API на Flask + простий
веб-інтерфейс (SPA) + мок інтеграції з Azure AI Foundry, що дозволяє
запустити систему без реального ключа.

> Повні вимоги — у [`PRD.md`](PRD.md), архітектура та схема БД —
> у [`Architecture.md`](Architecture.md).

## Можливості MVP

- 🔐 Автентифікація логін/пароль із видачею JWT
- 👤 Менеджмент користувачів, ролей і скидання паролів (Admin)
- 👥 Групи, членство, ролі в групі, правило «мінімум 1 менеджер»
- 🧩 **Каталог навичок**: керується лише завантаженням пакетів; статуси
  **«Не опублікована» / «Опублікована»**; обов'язкові атрибути (назва, версія,
  автор, опис, категорія) зі `skill.md` з можливістю редагування; завантаження
  нової версії в контексті навички; видалення чистить усі зв'язки
- 💬 **Чат із обраною моделлю** — користувач обирає LLM-модель зі списку
  активних, веде багатоходовий діалог (з історією) і за бажанням **застосовує
  скіли** до повідомлень
- 🔗 Підключення моделей кількох провайдерів — **Azure OpenAI, OpenAI, Gemini**
  (тільки Admin); провайдер обирається для кожної моделі окремо
- 🗂️ **Керування каталогом моделей** (Admin): додавання, видалення та
  активація/деактивація; **лише активні** моделі доступні користувачам у чаті
- ⚡ Подвійне призначення скілів: групове + самостійна активація, з коректним
  лічильником унікальних активацій
- 🧱 **Скіли-пакети** — завантаження скіла як архіву (`.zip`/`.skill`) зі
  `skill.md`, кодом і файлами/папками; система **реально виконує Python-код**
  пакета в ізольованому підпроцесі (таймаут, ліміти ресурсів, чисте середовище)
- 📁 **Файли користувача** — кожному користувачу виділяється окреме сховище
  (підкаталог з GUID-назвою); файли, **створені кодом скіла**, зберігаються
  туди назавжди й доступні для завантаження, а також можна завантажувати власні
- ⚙️ Запуск скілів як одноразової дії (вкладка «Мої скіли»)
- 📊 Облік токенів — **вхідні / вихідні / загальні** — на рівні повідомлення,
  сесії, користувача, групи та глобально
- ⚙️ **Системна модель**: Admin може позначити одну LLM-модель «системною» —
  платформа використовує її для службових задач (перша — **авто-іменування
  чатів** за першим повідомленням, асинхронно). Системне використання токенів
  обліковується **окремо** від користувацького — по входу/виходу, моделях і
  фічах (`GET /usage/system`), і не входить у квоти користувачів.
- 🎚️ **Тижневі квоти токенів**: системна квота за замовчуванням (2000/тижд,
  задає Admin) + опційна **персональна квота** користувача з пріоритетом;
  власний лічильник у кожного користувача, **стильна шкала** у топбарі в
  реальному часі; при вичерпанні виклики моделей блокуються (429). Лічильники
  **скидаються щопонеділка о 00:05 UTC** (планувальник + «ліниве» скидання)

## Швидкий старт

### 1. Передумови
- Python **3.11+**
- `pip` та `venv`

### 2. Клонування та віртуальне середовище

```bash
git clone <repo-url>
cd smart-digital-skills

python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
```

### 3. Встановлення залежностей

```bash
pip install -r requirements.txt
```

### 4. Налаштування середовища

```bash
cp .env.example .env
```

За потреби відредагуйте `.env` (секрети, початковий пароль адміна).
Для MVP усе працює зі значеннями за замовчуванням, а всі LLM-провайдери —
у режимі моку (`LLM_MOCK=1`).

### 5. Ініціалізація бази та початкові дані

```bash
python -m scripts.init_db    # створює/синхронізує схему БД у instance/profihub.db
python -m scripts.seed       # наповнює демо-даними (ролі, користувачі, скіл)
```

> **Оновлення наявної бази.** Схема синхронізується автоматично: при старті
> застосунку (і в `init_db`) виконується легка additive-міграція, яка дописує
> нові nullable-колонки до існуючих таблиць. Тож після `git pull` зазвичай
> **не потрібно** видаляти `instance/profihub.db`. Вимкнути авто-міграцію:
> `AUTO_MIGRATE=0` у `.env`.

### 6. Запуск

```bash
python wsgi.py
```

Відкрийте **http://localhost:5000** у браузері.

> Production-запуск: `gunicorn wsgi:app` (додайте `gunicorn` у середовище).

## Демо-облікові записи

Створюються скриптом `seed`:

| Роль | Логін | Пароль |
| --- | --- | --- |
| Адміністратор системи | `admin` | `Admin123!` |
| Skill-менеджер | `skillmanager` | `Skill123!` |
| Користувач (member) | `user1` | `User123!` |
| Користувач (member) | `user2` | `User123!` |

> Паролі адміна можна змінити через `ADMIN_USERNAME` / `ADMIN_PASSWORD` у `.env`
> **перед** запуском `seed`.

### Що подивитися після входу
- **будь-який користувач** — вкладка **«Чат»**: оберіть модель, ведіть діалог,
  за бажанням застосуйте скіл до повідомлення; токени рахуються в реальному часі.
- **admin** — усі вкладки: чат, користувачі, моделі (додати/видалити/активувати),
  групи, управління скілами, токени.
- **skillmanager** — завантаження/публікація навичок (без доступу до користувачів).
- **user1 / user2** — «Каталог»: пошук навичок, встановлення/вилучення, запуск Summarizer.

## Чат із моделлю та скіли

«Чат» — головний робочий простір користувача:

1. Оберіть **активну LLM-модель** зі списку та створіть сесію.
2. Спілкуйтеся — історія діалогу передається моделі (до 20 останніх повідомлень).
3. За потреби виберіть **скіл** у випадному списку: його prompt-шаблон
   застосується до вашого повідомлення (текст підставляється у параметр `text`
   або перший параметр скіла). Генерація все одно йде через **обрану модель чату**.
4. Під кожним повідомленням і в підсумку сесії показано облік токенів
   (**вхідні / вихідні / загальні**).

Доступні для вибору лише **активні** моделі. Активацією/деактивацією та
видаленням моделей керує адміністратор у вкладці «Моделі». Модель, яку
використовує хоча б один скіл, видалити не можна — спершу деактивуйте її або
переналаштуйте скіли.

## Менеджмент каталогу навичок

Керування каталогом просте й кероване пакетами:

1. **Створення лише завантаженням** — ручного створення навичок через форму
   немає. Admin/Skill Manager завантажує архів (`.zip`/`.skill`) зі `skill.md`.
2. **Статуси**: щойно завантажена навичка — **«Не опублікована»** (`draft`).
   Опублікувати / зняти з публікації може Admin або менеджер каталогу.
   Користувачам доступні лише опубліковані навички.
3. **Обов'язкові атрибути** — Назва, Версія, Автор, Опис, Категорія — читаються
   з фронтматеру `skill.md` (`name`, `version`, `author`, `description`,
   `category`) і редагуються в UI для кожної навички.
4. **Версіонування**: завантаження пакета *без контексту* створює нову навичку;
   завантаження *в контексті наявної навички* (в її картці редагування) — це
   нова версія тієї самої навички: активації та призначення групам зберігаються.
5. **Скачування**: пакет будь-якої навички можна скачати з менеджменту.
6. **Видалення** прибирає і всі зв'язки навички з групами та користувачами —
   після повторного встановлення її потрібно активувати заново.

## Навички-пакети (виконання коду)

Система підтримує навички у **стандартному форматі Agent Skills**
(як у Claude/ChatGPT) — архіви `.zip`/`.skill` зі `SKILL.md`,
кодом та будь-якими файлами/папками. Навички **не треба
переписувати під платформу** — використовуються як є.

Є два режими (визначаються наявністю `entrypoint` у `SKILL.md`):

- **Агентний (стандартний, без `entrypoint`):** `SKILL.md` (інструкції) і файли
  передаються **моделі**; модель сама виконує bundled-скрипти у код-пісочниці
  (виводить блок ` ```run-python ` → платформа виконує його й повертає результат)
  до 6 кроків. Так працюють типові Claude/ChatGPT-скіли: модель читає
  методологію, обчислює відповідь динамічно та викликає допоміжні скрипти
  (напр. `from build_estimate import build_estimate`).
- **Скрипт (з явним `entrypoint`):** платформа просто виконує вказаний файл,
  передавши вхідні дані на stdin (детермінований режим, без виклику моделі).

### Структура пакета

```
my-skill.zip
├── skill.md            # метадані (YAML-фронтматер) + інструкції
├── main.py             # entrypoint, що виконується
├── lib/                # будь-які вкладені файли та папки
│   └── counter.py
└── ...
```

`skill.md` з YAML-фронтматером:

```markdown
---
name: Word Counter
description: Підраховує слова та символи у тексті.
version: 1.0.0
runtime: python
entrypoint: main.py
inputs:
  - name: text
    label: Текст
    required: true
  - name: uppercase
    required: false
    default: ""
---
# Інструкції (тіло markdown)
```

### Контракт виконання

- entrypoint отримує на **stdin** JSON виду `{"inputs": {...}}`;
- має вивести у **stdout** результат: або звичайний текст, або JSON
  `{"output": "...", "usage": {"prompt_tokens": N, "completion_tokens": M}}`
  (поле `usage` опціональне — використовується для обліку токенів);
- ненульовий код виходу або вивід у stderr трактуються як помилка.

Готовий приклад: [`examples/skills/word-counter/`](examples/skills/word-counter)
(його `seed` автоматично пакує та реєструє як демо-скіл **Word Counter**).

> **Визначення entrypoint гнучке:** `skill.md` може містити `entrypoint`
> (шлях відносно кореня пакета, напр. `scripts/build_estimate.py`; допускається
> й `./`). Якщо його не вказано — система шукає `main.py` у пакеті; якщо в пакеті
> лише один `.py` файл, використовується він. Архів може мати одну верхню теку
> (`my-skill/skill.md`, …) або файли в корені — обидва варіанти працюють.
>
> **Вкладений entrypoint та імпорти:** при виконанні у `sys.path` додаються і
> корінь пакета, і тека самого скрипта, тож код може імпортувати як модулі з
> кореня (`from common import …`), так і сусідні файли (`from helper import …`)
> без ручного налаштування шляхів.

### Безпека та ізоляція

Виконання довільного коду — потенційно небезпечне, тож реалізовано з обмеженнями:

- завантажувати пакети можуть **лише Admin/Skill Manager** (RBAC);
- код запускається в **окремому підпроцесі** (`python -I`) у тимчасовій теці,
  яка видаляється після виконання;
- **таймаут** (`SKILL_EXEC_TIMEOUT`), ліміти CPU та розміру файлів, опційний
  ліміт пам'яті (`SKILL_EXEC_MEMORY_MB`), обмеження розміру виводу;
- **чисте середовище** (секрети застосунку не передаються), захист від
  zip-slip та zip-bomb;
- глобальний вимикач `SKILL_EXEC_ENABLED=0` повністю забороняє виконання;
- виконання у **UTF-8-режимі** (`python -X utf8`) — кирилиця/емодзі у виводі та
  назвах файлів коректні на будь-якій ОС, зокрема **Windows** (де локаль cp1251).

> ⚠️ Найкращий захист — додаткова ізоляція на рівні ОС: запускайте застосунок
> у контейнері/VM з обмеженим доступом до мережі та файлової системи.
> Залежності з `requirements.txt` усередині пакета **не** встановлюються
> автоматично — потрібні бібліотеки мають бути в середовищі застосунку.

## Файли користувача

Кожному користувачу виділяється **окреме постійне сховище** — підкаталог з
автоматично згенерованою GUID-назвою (замість імені):

```
instance/user_files/<GUID>/         # напр. a7c4d18fd4944b5bbc03ea3850046c9c/
├── 1_report.txt
├── 2_data.csv
└── ...
```

- **Файли, створені кодом скіла-пакета** під час виконання (будь-який файл, що
  його код записує у свою робочу теку), автоматично зберігаються у сховище того
  користувача, який запустив скіл, і **залишаються назавжди**.
- Після запуску у відповіді (та в UI — у чаті й у вкладці «Мої скіли») зʼявляються
  **кнопки завантаження** створених файлів.
- Користувач також може **завантажувати власні файли** у вкладці «Файли»
  (випадок «без скіла»).
- Файли **ізольовані**: користувач бачить і звантажує лише власні файли
  (перевірка власника на кожному запиті). GUID-назва теки приховує особу власника
  на рівні файлової системи.

**Клікабельні посилання.** Кожен файл має пряме посилання виду
`http://<host>/files/<GUID>/<FILENAME>`, де `<GUID>` — `storage_uid` користувача,
а `<FILENAME>` — назва файлу. Хост відповідає поточному (посилання будується від
`window.location`). Коли скіл створює файл, у чаті зʼявляється таке клікабельне
посилання. GUID виступає неперебірним капабіліті-токеном.

Файли (і робоча тека виконання скілів) зберігаються **всередині застосунку**
(`instance/user_files/`, `instance/run_tmp/`), а не у `/tmp`. Каталог і ліміт
розміру налаштовуються через `USER_FILES_DIR` та `USER_FILE_MAX_BYTES`. Окрім
публічного посилання, є й автентифікований ендпоінт `/api/files/{id}/download`.

> Демо: запустіть скіл **Word Counter** з параметром «Зберегти звіт у файл» —
> зʼявиться `report.txt`, доступний для завантаження.

## Квоти токенів (тижневі)

- **Системна квота** діє для всіх користувачів за замовчуванням
  (`DEFAULT_WEEKLY_TOKEN_LIMIT`, 2000/тиждень). Admin змінює її у вкладці
  «Користувачі» → «Системна тижнева квота».
- **Персональна квота** користувача — опційна; якщо встановлена, **має пріоритет**
  над системною. Admin задає / оновлює / видаляє її там же (кнопки «Задати/Змінити»
  та «✕ квота»).
- У кожного користувача — **власний тижневий лічильник** використаних токенів.
  У топбарі відображається **шкала квоти** (використано / ліміт) у реальному часі,
  колір змінюється зелений → бурштиновий → червоний.
- При вичерпанні квоти виклики моделей блокуються (HTTP **429**).
- **Скидання — щопонеділка о 00:05 UTC**: фоновий планувальник (APScheduler)
  обнуляє лічильники; додатково діє «ліниве» скидання за зсувом тижневого вікна
  (коректно навіть після рестарту чи пропущеного запуску). Вимкнути планувальник:
  `ENABLE_SCHEDULER=0`.

## LLM-провайдери (Azure OpenAI · OpenAI · Gemini)

Кожна модель у реєстрі має поле `provider`. Під час запуску скіла фабрика
(`app/integrations/__init__.py`) обирає відповідний клієнт за провайдером моделі:

| `provider` | Синоніми | Клієнт | Ключі у `.env` |
| --- | --- | --- | --- |
| `azure_ai_foundry` | `azure_openai`, `azure` | Azure OpenAI | `AZURE_FOUNDRY_ENDPOINT`, `AZURE_FOUNDRY_API_KEY` |
| `openai` | — | OpenAI API | `OPENAI_API_KEY` (опц. `OPENAI_BASE_URL`) |
| `gemini` | `google` | Google Gemini | `GEMINI_API_KEY` |

`deployment_name` моделі — це ідентифікатор моделі у провайдера
(напр. `gpt-4o` для Azure/OpenAI, `gemini-1.5-pro` для Gemini).

У MVP усі провайдери працюють **у режимі моку** (`LLM_MOCK=1`), тож застосунок
запускається без жодних ключів. Щоб увімкнути реальні виклики:

1. Встановіть потрібний SDK:
   - OpenAI / Azure OpenAI: `pip install openai`
   - Gemini: `pip install google-generativeai`
2. У `.env` поставте `LLM_MOCK=0` і задайте ключі відповідного провайдера.
3. Зареєструйте модель з потрібним `provider` (вкладка «Моделі» або `POST /api/models`).

Доступні провайдери для UI повертає `GET /api/models/providers`.

## Наступні етапи (поза MVP)

- **Етап 2:** SSO через Entra ID (OIDC), детальні місячні ліміти токенів
  (`token_limits`) та аналітика/графіки. Поля під це вже закладені у схему.
